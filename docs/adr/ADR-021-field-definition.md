# ADR-021: Immutable FieldDefinition With Explicit Type Ownership and Value-Type Declaration (TYPE-02)

## Status

Accepted for TYPE-02.

## Context

In enterprise model-driven platforms, type-level models alone are insufficient; applications require granular definitions for properties, attributes, and fields belonging to authored types.

In conventional frameworks, field modeling is frequently distorted by:
1. **Conflation with Runtime Values:** Storing mutable instance state (`currentValue`, `FieldValue`) inside the field definition contract.
2. **Coupling to Persistence/ORM:** Conflating semantic field definitions with database columns (`columnName`, `sqlType`, `isNullable`, `isPrimaryKey`).
3. **Coupling to Presentation/UI Frameworks:** Modeling fields directly as Angular FormControls, PrimeNG widgets, or validation directives.
4. **Name-Inferred Ownership:** Assuming that a field named `sales.Customer.name` is owned by `sales.Customer` simply because of string path hierarchy, rather than an explicit identity-and-version reference.
5. **Ambiguous or Mixed Value Types:** Using loose bags (`{ primitiveType?: string, typeRef?: any }`) that permit contradictory or missing value type declarations.
6. **Conflating Fields with Relationships:** Treating a field referencing another type as an entire relationship graph without explicit relationship semantics.

TYPE-02 defines the foundational `FieldDefinition` and `FieldType` contracts within the Pure TypeScript Model Core.

## Decision

### 1. Architectural Ownership in Model Core

`FieldDefinition` and `FieldType` belong to Layer C (**Model Core** / `@ecosystem/model-core`), residing under `platform/model/model-core/src/types/`. Model Core depends exclusively on `@ecosystem/semantic-kernel` and contains zero framework, ORM, database, or UI dependencies.

### 2. Independent, Stable Field Identity (SK-01)

Every `FieldDefinition` possesses its own `id: SemanticElementId`. A field's identity:
- Is independent of its containing `TypeDefinition` ID.
- Is never generated by string concatenation (`typeId + '.' + fieldName`).
- Remains stable across compatible revisions of its containing type (e.g. Customer v1.0.0 and Customer v1.1.0 can share the same field identity).
- Remains stable across field renames under explicit model evolution.

### 3. Explicit Type Ownership via ElementVersionRef (SK-07)

Every `FieldDefinition` explicitly identifies its containing type through `ownerType: ElementVersionRef`.
- **QualifiedName hierarchy does NOT prove ownership:** Even if a field is named `sales.Customer.name`, the explicit `ownerType` reference is the sole authoritative source of containment.
- **Snapshot Version Pinning:** The owner reference pins the exact `(elementId, version)` snapshot of the containing `TypeDefinition` where the field was declared.
- **Referential Integrity Boundary:** Local construction validates component authenticity (`instanceof ElementVersionRef`), but does not query registries or assume target existence.

### 4. Semantic Context Boundary (SK-04)

Every `FieldDefinition` carries an explicit `contextRef: SemanticContextRef`. In accordance with platform principles, **Context owns meaning**: two fields with identical names in different contexts represent distinct semantic concepts. Context is never inferred from tenant, environment, or namespace.

### 5. Fixed FIELD Classification (SK-06)

A `FieldDefinition` has a fixed classification: `kind: typeof SemanticElementKinds.FIELD` (`'field'`). It cannot be constructed with or morphed into `TYPE`, `ACTION`, `EVENT`, `POLICY`, or any other taxonomy code.

### 6. Strongly Discriminated FieldType System

The declared value type of a field is decoupled from its element classification and modeled as a strict discriminated union:
```typescript
export type FieldType =
  | PrimitiveFieldType   // { by: 'primitive', primitiveType: PrimitiveType }
  | ReferencedFieldType; // { by: 'reference', typeRef: ElementRef }
```
- **Primitive Variant:** Reuses SK-09 `PrimitiveType` (e.g. `STRING`, `BOOLEAN`, `INTEGER`, `DECIMAL`, `DATE`, `TIME`, `DATETIME`).
- **Referenced Variant:** Reuses SK-08 `ElementRef` (targeting authored semantic definitions).
- **Mutually Exclusive Variants:** Compile-time `never` properties and runtime factory validations prevent invalid mixed states (e.g. having both primitive and reference values).

### 7. Strict Immutability and Validated Construction

- Concrete instances (`ImmutableFieldDefinition`) are deeply frozen (`Object.freeze`).
- No public setters or mutable collections exist.
- Factory `createFieldDefinition(...)` enforces runtime authenticity for all Kernel value objects and rejects non-objects, spoofed objects, or raw strings.
- Deserialization `parseFieldDefinition(...)` reconstructs all constituent Kernel value objects through approved parsers.

### 8. Strict Scope Boundaries & Deferred Capabilities

To avoid premature complexity:
- **No Runtime Field Values:** Definition metadata contains no instance data.
- **No Nullability or Optionality Engine:** Deferred to dedicated type-system milestones.
- **No Cardinality / Repeated Fields:** Deferred to future type-system tasks.
- **No Constraints Engine:** Range, regex, length, and uniqueness constraints are deferred.
- **No Default Value Evaluation:** Computed expressions and runtime defaults are deferred.
- **No Relationship Modeling:** Authored type references represent value types, not relationship graphs.
- **No Persistence or UI Mapping:** Zero SQL, ORM, Angular, or PrimeNG couplings.

## Consequences

- **Positive:** A mathematically sound, immutable, strongly typed field contract in Model Core.
- **Positive:** Clean separation between field identity (`SemanticElementId`) and owner version pinning (`ElementVersionRef`).
- **Positive:** Robust discriminated union for `FieldType` preventing invalid, ambiguous, or untyped states.
- **Positive:** 100% portable Pure TypeScript without external runtime or framework dependencies.
- **Trade-off:** Consumers requiring runtime instance validation, field constraints, or relationships must await subsequent platform milestones.
