## 6. Fundamental Definition

Define:

**QualifiedName**

A QualifiedName represents the canonical name of a semantic element within an explicitly identified Namespace.

Conceptually:

```text
QualifiedName
├── Namespace
└── LocalName
```

Example:

```text
Namespace: sales
LocalName: Customer

QualifiedName: sales.Customer
```

It is a naming construct, not a stable identity construct.

---

Preserve:

```text
QualifiedName ≠ SemanticElementId
QualifiedName ≠ Namespace
QualifiedName ≠ SemanticContextRef
QualifiedName ≠ SemanticVersion

QualifiedName ≠ ElementRef
QualifiedName ≠ TenantId
QualifiedName ≠ OrganizationId
QualifiedName ≠ Database Key
QualifiedName ≠ Filesystem Path
QualifiedName ≠ Authorization Scope

A QualifiedName identifies a semantic name in an explicitly defined naming system.

It does not independently prove which registered element exists behind that name.

## 8. Semantic Identity Versus Naming

For example:

```

If a future authorized model evolution renames the element:

```text

        ↓

```

the SemanticElementId may remain the same.

Do not infer stable identity solely from QualifiedName equality.

Do not generate SemanticElementId from QualifiedName text.

## 10. Local Name Contract

QualifiedName requires one local name.

A local name is the name of one semantic element within its Namespace.

Examples:

```text
Customer
Employee
Order
Invoice
CustomerAddress
```

Do not confuse a local name with a complete Namespace.

Do not permit the local name to contain the namespace separator when the selected grammar uses `.`.

Do not implement an independent public `LocalName` value object unless a real repository convention already requires it.

A private validated local-name contract is sufficient for SK-03.

## 11. Local Name Grammar

Inspect whether the repository already defines local element-name syntax.

If not, choose a grammar compatible with SK-02's namespace segments.

Recommended v0:

```text
localName := firstCharacter subsequentCharacter*

firstCharacter := ASCII letter

subsequentCharacter := ASCII letter | digit | "_"
```

Valid examples:

```text
Customer
Employee
Order123
Customer_Address
invoice
```

Invalid examples:

```text
""
"123Customer"
"Customer-Address"
"Customer Address"
"Customer.Address"
"/Customer"
" Customer"
"Customer "
```

Do not adopt a grammar that makes valid SK-02 Namespace values impossible to combine with valid local names.

Document any deliberate difference between Namespace segment grammar and local-name grammar.

## 12. QualifiedName Grammar

Under SK-02's recommended dotted Namespace syntax, define:

```text
qualifiedName := namespace "." localName
```

Examples:

```text
sales.Customer
sales.Employee
enterprise.sales.Customer
finance.Invoice
operations.inventory.StockItem
```

The separator must come from the established SK-02 convention.

Do not create another unapproved separator.

Do not use namespace-string concatenation without validating both components.

---

## 13. At Least One Namespace Segment

A QualifiedName must contain:

- A valid Namespace.
- Exactly one local element-name segment.

Under the recommended grammar:

```text
Customer
```

is not a complete QualifiedName.

```text
sales.Customer
```

is a complete QualifiedName.

Do not invent an implicit global/default Namespace.

If the existing platform explicitly defines a root Namespace, follow that actual contract; do not fabricate one here.

---

## 14. Parsing Ambiguity Resolution

The dotted grammar permits namespaces of multiple segments.

For a string:

```text
enterprise.sales.Customer
```

parse it as:

```text
Namespace:
    enterprise.sales

LocalName:
    Customer
```

The final separator divides the Namespace from the local name.

Do not use the first separator.

Do not treat the whole string as a Namespace without extracting the local name.

Do not attempt registry lookup to determine where the split should occur.

This is purely syntactic parsing.
