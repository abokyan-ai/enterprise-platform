## 6. Namespace Definition

Define:

**Namespace**

A Namespace represents a canonical semantic naming scope used to organize semantic names.

It is not itself a semantic element identity unless a future explicit model defines a namespace element.

It must be:

- Strongly typed.
- Immutable.
- Validated.
- Canonical.
- Comparable by value.
- Independent of frameworks.
- Independent of storage representations.
- Suitable for serialized interchange.

Namespace names must have clear syntactic semantics.

Do not require a semantic registry merely to construct a syntactically valid Namespace.

---

## 7. Fundamental Distinctions

Preserve:

```text
Namespace ≠ SemanticElementId
Namespace ≠ QualifiedName
Namespace ≠ SemanticContextRef
Namespace ≠ TenantId
Namespace ≠ OrganizationId
Namespace ≠ PackageId
Namespace ≠ Database Schema
Namespace ≠ Filesystem Directory
Namespace ≠ URL
Namespace ≠ Authorization Scope
Namespace ≠ Runtime Registry
```

Namespace organizes names.

SemanticElementId provides stable identity.

SemanticContextRef determines a semantic context.

QualifiedName, implemented later, associates a namespace with a local name according to its own contract.

Do not conflate these concepts.

## 8. Naming Scope Versus Identity

An element can retain the same SemanticElementId after a permitted rename or namespace reassignment under later model-evolution rules.

Conceptually:

```text
SemanticElementId:
    typ_customer_123

Previous Namespace:
    sales

New Namespace:
    enterprise.sales
```

Namespace changes do not automatically mean the element's stable identity must change.

Do not implement rename or migration operations in SK-02.

Do not construct SemanticElementId by concatenating namespace text.

## 9. Namespace Grammar

Inspect the existing repository for established naming rules.

If no authoritative namespace grammar exists, adopt a small, explicit, portable dotted-segment grammar.

Recommended v0:

```text
namespace := segment ("." segment)*

segment := first_character subsequent_character*

first_character := ASCII letter

subsequent_character := ASCII letter | digit | "_"
```

Examples:

```text
sales
human_resources
enterprise.sales
enterprise.sales_2026
finance.accounts_payable
```

Do not use `.` as part of an individual segment.

The chosen grammar must be documented and enforced consistently.

Do not support arbitrary URI syntax, filesystem paths, or wildcard expressions.

---

## 10. Grammar Authority

The grammar selected for SK-02 becomes the canonical contract for Namespace.

Do not establish one grammar for parsing and another for serialization.

Do not allow NestJS, Angular, or Compiler adapters to reinterpret Namespace syntax.

Do not use framework-specific validators to define Kernel semantics.

If an actual existing repository specification conflicts with the recommended v0 grammar, preserve the established specification and document the decision.

## 13. Segment Requirements

Each segment must be nonempty.

Reject:

```text

```

Do not remove empty segments automatically.

Do not create implied default segments.

## 14. Case Sensitivity

Define and document case semantics.

Recommended:

**Namespace is case-sensitive and preserves canonical spelling.**

Under this rule:

```text
sales
Sales
SALES
```

are three different Namespace values.

Do not lowercase input automatically.

Do not perform locale-dependent case folding.

Do not assume database collation defines namespace equality.

If an existing platform-wide naming convention requires lowercase-only namespaces, follow that convention consistently instead.

Do not leave this behavior unspecified.

## 15. Whitespace Policy

Reject leading, trailing, or embedded whitespace not explicitly permitted by the chosen grammar.

Do not silently trim:

```typescript

```

before validating.

A caller that wishes to clean authoring input must do so at its own explicit application boundary.

The Kernel validates canonical namespace values.

It does not guess user intent.

## 16. Unicode Policy

Do not add unrestricted Unicode support without a documented normalization, security, and interoperability policy.

Do not apply locale-specific normalization.

Do not treat visually similar Unicode characters as automatically equal.

Future internationalized naming can be introduced through a deliberate contract evolution.

## 28. Parent Namespace

If implemented, use:

```typescript

```

or a compatible explicit optional result.

Do not invent an implicit empty root Namespace.

Do not automatically query a namespace registry.

Parenthood is syntactic, not proof of registered semantic hierarchy.
