## 6. Definition of SemanticElementKind

Define:

**SemanticElementKind**

It represents the declared semantic category of a semantic definition.

It answers:

> What kind of semantic definition is this element?

It does not answer:

- What business domain does it belong to?
- What data does an instance contain?
- How does the Compiler process it?
- How does the Runtime execute it?
- Which database stores it?
- Which user may access it?

The classification must be explicit, stable, validated, serializable, and independent of framework implementations.

---

## 7. Core Classification Principle

Preserve:

**Unify the semantic language, not every domain ontology.**

The platform needs a shared classification language.

It does not need one universal taxonomy containing every business concept.

Distinguish:

```text
Semantic Element Kind
    → Platform-level semantic category.

Business Domain Type
    → Domain-specific semantic definition.

Runtime Instance
    → Data governed by a compiled definition.
```

Do not classify `Customer`, `Invoice`, or `Employee` as built-in Kernel kinds.

Those are domain concepts, not foundational classification categories.

## 15. Open Versus Closed Classification

Make the distinction explicit.

A closed set:

- Rejects unrecognized kinds.
- Provides compile-time narrowing.
- Gives stable documented categories.
- Supports exhaustive handling by consumers.

An open set:

- Allows externally defined categories.
- Requires collision protection.
- Requires namespace or ownership semantics.
- Requires registration and compatibility policy.

For SK-06, do not introduce an open runtime registration mechanism unless the existing platform already defines it.

Prefer a documented closed foundational baseline.

Do not make arbitrary plugin strings authoritative Kernel kinds.

## 49. Example Pure TypeScript API

The following is an illustrative design, not an exact mandatory implementation:

```typescript
export const SemanticElementKinds = Object.freeze({
  TYPE: 'TYPE',
  FIELD: 'FIELD',
  RELATIONSHIP: 'RELATIONSHIP',
  ACTION: 'ACTION',
  EVENT: 'EVENT',
  POLICY: 'POLICY',
} as const);

export type SemanticElementKind =
  (typeof SemanticElementKinds)[
    keyof typeof SemanticElementKinds
  ];

export function isSemanticElementKind(
  value: unknown,
): value is SemanticElementKind {
  return (
    typeof value === 'string' &&
    Object.values(SemanticElementKinds).some(
      (kind) => kind === value,
    )
  );
}

export function parseSemanticElementKind(
  value: unknown,
): SemanticElementKind {
  if (!isSemanticElementKind(value)) {
    throw new TypeError(
      'Invalid semantic element kind',
    );
  }

  return value;
}
```

This is illustrative.

Do not assume the listed categories are the final authoritative taxonomy.

Inspect the repository first.

Adapt to existing error conventions and public exports.

Avoid duplicated canonical lists.
