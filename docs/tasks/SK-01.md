## 6. Core Identity Definition

Define:

**SemanticElementId**

It represents the unique, stable identity of one semantic element within the platform's defined identity domain.

It must be:

- Opaque.
- Immutable.
- Strongly typed.
- Explicitly validated.
- Comparable by value.
- Independent of display names.
- Independent of namespace naming.
- Independent of semantic versions.
- Independent of persistence technology.

The identity must remain stable when the element's descriptive attributes change.

Do not derive the identity from display text.

## 8. Identity Stability

The same semantic element must retain its SemanticElementId when:

- Its display name changes.
- Its descriptive documentation changes.
- Its canonical representation changes.
- Its physical storage representation changes.
- A new semantic version is introduced under the platform's later versioning rules.

Do not automatically generate a new identity from a renamed QualifiedName.

Do not use content hashes as element identity.

Do not calculate identity from compiled artifact bytes.

## 9. Opaque Representation

Consumers must treat SemanticElementId as an opaque value.

Do not encourage business logic such as:

```typescript
if (id.startsWith('customer')) {
  // infer semantic meaning
}
```

An identifier's representation may be human-readable for debugging, but its prefixes must not become authoritative semantic classification.

Do not parse namespace or semantic version from SemanticElementId.

## 11. Identifier Validation

Implement explicit validation.

The validation contract must define:

- Accepted input type.
- Empty-value rejection.
- Whitespace handling.
- Maximum length.
- Accepted characters or canonical identifier grammar.
- Canonical representation.
- Rejection of malformed values.

Do not silently trim input unless the identity contract explicitly specifies normalization.

Prefer rejecting ambiguous input over silently changing identity.

Do not accept `null`, `undefined`, numbers, objects, or arrays as valid identifier values.

## 12. Canonicalization

Define whether the chosen identity grammar permits normalization.

Prefer a single canonical representation.

If using UUIDs, specify case and structural canonicalization.

If using opaque prefixed IDs, specify allowed syntax precisely.

Avoid identity collisions caused by unintended case folding.

Do not apply Unicode normalization indiscriminately.

Do not confuse identifier canonicalization with Semantic Model canonicalization.

---

## 13. Case Sensitivity

Make case sensitivity explicit.

Either:

- Require one canonical case; or
- Preserve case and treat differently cased values as distinct identities.

Do not let equality depend on locale-sensitive case conversion.

Do not make browser locale settings affect SemanticElementId.

Document the selected rule.

## 14. Immutability

Implement SemanticElementId as a real immutable value object.

Its internal value must not be writable after construction.

Do not expose a public mutable field.

If using a class, use appropriate TypeScript encapsulation and runtime protection where necessary.

Do not rely on `readonly` alone as proof that arbitrary JavaScript callers cannot mutate a publicly exposed property.

Avoid unnecessary inheritance.

## 15. Strong Typing

Prevent accidental mixing of semantic IDs with arbitrary strings where practical.

A recommended approach is an immutable class or an explicitly branded value type.

Do not introduce dozens of identity wrappers without a current need.

The public API must make invalid construction difficult.

Prefer:

```typescript
const id = SemanticElementId.parse(rawValue);
```

over unchecked string casts.

Do not encourage:

```typescript

```

as the ordinary construction path.

## 17. Parse Failure Contract

Invalid input must fail predictably.

Choose a narrow, typed failure mechanism compatible with the existing Semantic Kernel conventions.

For example:

```typescript

```

may throw a dedicated documented validation error.

A nonthrowing API may return a typed discriminated union:

```typescript
type ParseResult<T> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: IdentityValidationError };
```

This is illustrative.

Do not introduce a generic platform Result framework solely for SK-01.

Do not invent a full SK-11 diagnostics system before that task exists.

## 18. Nonthrowing Validation

## 19. Equality Semantics

Two SemanticElementId values are equal if and only if their canonical identity representations are equal.

Conceptually:

```typescript
const first = SemanticElementId.parse('typ_customer_123');
const second = SemanticElementId.parse('typ_customer_123');

first.equals(second); // true, if this format is approved
```

The example is illustrative; use identifiers valid under the implemented grammar.

Do not use object reference equality as the semantic equality contract.

Do not compare labels or QualifiedNames.

Do not compare semantic versions.

## 20. Inequality Semantics

Do not apply fuzzy matching.

Do not infer equality from similar prefixes.

Do not compare identity based on an element's display name.

Do not treat two separately created semantic elements as identical merely because their definitions have equal content.
