## 6. Definition of SemanticElement

Define:

**SemanticElement**

A SemanticElement is a semantic definition-level object recognized by the platform's common semantic language.

It is not a runtime business-data instance.

The base contract describes the minimum common structural properties required to identify and name an element within a semantic context.

At this stage, those properties should be limited to existing, established Kernel primitives.

Recommended minimum:

```text
SemanticElement
├── SemanticElementId
├── QualifiedName
└── SemanticContextRef
```

Treat this as a proposed minimal contract.

If the actual repository already establishes a smaller or different authoritative base contract, preserve that agreement and document the choice.

Do not add speculative fields merely because future element types may need them.

## 9. Minimal Contract Shape

Prefer a TypeScript interface or equivalent compile-time contract.

```typescript

  readonly id: SemanticElementId;
  readonly qualifiedName: QualifiedName;
  readonly contextRef: SemanticContextRef;
```

Use actual repository naming conventions.

- `kind`
- `version`
- `metadata`
- `facets`
- `annotations`
- `status`
- `createdAt`

because their meanings and ownership are not yet established by SK-05.

Do not introduce fields whose semantics belong to future tasks.

## 10. Contract Versus Concrete Class

Distinguish a structural contract from a concrete implementation.

An interface defines required properties.

An immutable class or validated factory can provide runtime construction invariants where actually needed.

Do not create a mandatory inheritance-based SemanticElement superclass solely because the task contains the phrase "Base Contract."

Prefer composition over inheritance.

If a concrete implementation is justified, keep it minimal and avoid framework-specific behavior.

Do not create a class hierarchy that every future semantic definition must extend.

## 11. Immutable Contract Semantics

All base properties must be readonly.

However, TypeScript readonly modifiers provide compile-time guarantees, not comprehensive runtime deep immutability.

Where a concrete factory or value object is implemented, enforce appropriate runtime immutability.

Do not expose mutable internal collections.

Do not introduce setters for semantic identity, name, or context.

Do not make a semantic element mutate itself in response to renaming.

## 15. Context Owns Meaning

## 16. Identity and Context Independence

The base contract includes both identity and context without requiring one to encode the other.

Do not derive context from identifier prefixes.

## 17. No Implicit Uniqueness Registry

The SemanticElement contract cannot, by itself, prove global uniqueness.

A local factory can validate the shape and types of fields.

It cannot prove:

- No other element uses the same ID.
- No other element has the same name in a context.
- An element is registered.
- An element is discoverable.
- An element is authorized.

Those require a trusted collection, registry, or resolver in a future task.

Do not fabricate those capabilities.

## 18. Element Equality

Distinguish possible equality concepts.

**Stable identity equality** compares SemanticElementId.

**Contextual naming equality** compares context and qualified name.

**Structural equality** compares element definition content.

These are not interchangeable.

SK-05 must not invent a universal `equals()` method that ambiguously chooses among them.

If the base contract provides an equality helper, its semantics must be explicit.

Prefer relying on SK-01's ID equality until a broader semantic equality policy exists.
